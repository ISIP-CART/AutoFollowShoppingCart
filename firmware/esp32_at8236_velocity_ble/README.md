# ESP32 + AT8236 速度闭环 BLE 控制固件

> **当前推荐烧录**：这是本仓库当前唯一推荐用于实车 BLE 手动控制和自动跟随的
> 下位机固件。`firmware/esp32_at8236_openbot_ble/` 仅保留为早期联调历史版本。

这是当前实车速度验证程序的 BLE 集成版。它保留已经通过阶段 A-M 的 AT8236
参数、四轮方向、`$spd` 速度闭环、`$MSPD` 故障检测和主动制动，不沿用早期 BLE
版本中的旧电机类型、轮间 trim、低速 kick 或普通停车立即 `$pwm:0` 的策略。

## 文件与适用范围

- 烧录草图：`esp32_at8236_velocity_ble.ino`
- 开发板：ESP32 Dev Module / ESP32-WROOM-32E
- 上位机：本仓库 OpenBot Android 的 `RealCartFollowFragment`
- 控制方式：Android 左右逻辑量 -> ESP32 四轮映射 -> AT8236 `$spd` mm/s 闭环
- 当前只开放差速前进、后退、原地转向和弧线，不开放麦轮横移
- 已集成中央 URM09-I²C 与左右 VL53L1X；当前为仅日志模式，不参与运动许可或停车
- 阶段 N 载物测试保持暂停；先完成 BLE 空载联调

## 接线与 AT8236 参数

- ESP32 GPIO17 / TX2 -> AT8236 RX2
- ESP32 GPIO16 / RX2 <- AT8236 TX2
- ESP32 GND -> AT8236 GND
- 串口：115200, 8N1，无流控

固件写入并使用以下实车参数：

- `$mtype:2#`
- `$mphase:30#`
- `$mline:11#`
- `$wdiameter:80.000#`
- `$deadzone:1600#`
- `$upload:1,1,1#`

固件不覆写已验证的 MPID。卖家示例里 `mtype=2` 对应的 20:1、13 线、48 mm
是示例电机参数，不适用于本车。

## BLE 与 Android 兼容性

- 名称：`OpenBot: CART_AT8236`
- Service：`61653dc3-4021-4d1e-ba83-8b4eec61d613`
- RX：`06386c14-86ea-4d71-811c-48f97c58f8c9`
- TX：`9bf1103b-834c-47cf-b149-c9e4bcf778a7`
- RX：Write + Write Without Response
- TX：Notify + BLE2902

沿用 OpenBot 文本协议，每行以 `\n` 结束：

- `f`：回复 `fCART_AT8236:s:`；`:s:` 使现有 Android 启用测距显示，驱动遥测就绪后再回复 `r`
- `h750`：设置链路超时。Android 每 250 ms 发送一次
- `s100`：设置当前连接的 V1 测距上报周期（50–1000 ms，`s0` 关闭）
- `s<cm>`：固件按请求周期回传三路中“当前有效且未过期”的最小距离；无有效值时不伪造远距离
- `c<left>,<right>`：控制，Android 实车页面每 100 ms 重发当前值
- `c0,0`：普通停车，立即进入 `$spd:0` 主动制动
- `!S,<seq>`：锁存急停，必须重启 ESP32 才能恢复
- `!Q`：仅 USB，打印状态
- `!D,1` / `!D,0`：仅 USB，开关诊断日志

本版根据实车出现的 `state=DRIVER_ERROR`、同时 `mspd_age_ms=52` 且四轮已经为零的
日志，将“急停硬锁存”和“可恢复驱动瞬态故障”分开处理。启动时应额外看到：

```text
FAULT_RECOVERY,version=2,transient_auto_recover=1,overspeed_hard_ratio=3.00
```

本版还修复了 `c14` 的超速误锁停。实车故障快照中目标为 240 mm/s，而四轮 `$MSPD`
约为 419--438 mm/s；旧版 1.5 倍硬阈值只有 360 mm/s，因此会触发
`last_fault_reason=overspeed_m1`。现在 1.5 倍仅产生一次 `overspeed_warning` 诊断，
持续超过 3.0 倍动态阈值或 750 mm/s 绝对上限才进入不可恢复的 `DRIVER_ERROR`。
这只修正安全判定的误报，不表示实际轮速已经准确跟随 240 mm/s；仍需根据实测车速检查
AT8236 PID、编码器线数和轮径标定。

最新的 `购物车Android-ESP32通信协议V2草案.md` 仍标记为 `V2-DRAFT-0.1`，并明确
要求冻结前不实现 `m/d/g/a`。本固件因此只实现已兼容的 V1 `s` 能力；三路独立
距离、状态和 age 目前通过 USB `!Q` / `RANGE` 诊断查看。Android 页面上的 V1
数值只用于观察，不能作为当前固件具有防撞能力的依据。

## 三路测距与仅日志模式

I²C 总线为 100 kHz，全部模块按 3.3 V 供电：

| 位置 | 模块 | 接线 / 地址 | 有效范围（固件） |
|---|---|---|---:|
| 左前 | VL53L1X | SDA=21、SCL=22、XSHUT=25，启动后 `0x2A` | 40–1300 mm |
| 中央 | URM09-I²C | SDA=21、SCL=22，`0x11` | 20–5000 mm |
| 右前 | VL53L1X | SDA=21、SCL=22、XSHUT=26，启动后 `0x2B` | 40–1300 mm |

两只 ToF 先同时 XSHUT 拉低，再逐只释放、初始化和改址。ToF 使用 Short 模式、
33 ms timing budget、50 ms 连续测量；URM09 使用非阻塞的“触发—等待 100 ms—读取”
状态机，触发周期 120 ms。三路均维护 3 点有效值中值、原始设备状态、最后有效时间；
超过 200 ms 无有效更新视为不可用，不能当作前方空旷。

当前统一开关为：

```cpp
static const bool RANGE_MOTION_GATING_ENABLED = false;
```

- 三路仍计算中央 300/400 mm、左右 200/300 mm 风险锁存，供日志观察和后续标定。
- 开关关闭时，传感器缺失、过期或风险锁存均不得拒绝 `c` 命令，也不得调用制动。
- `REQUIRE_RANGE_SENSORS_FOR_MOTION=true` 被保留为未来重新启用门控后的策略参数，当前不生效。
- `c0,0`、急停、BLE 断连、心跳/运动刷新超时、驱动反馈故障和换向制动保持有效。
- 当前没有前向、侧向或后向防撞保证，只能先架空车轮并在空旷场地测试。

执行 `!D,1` 后，每 200 ms 输出一行 `RANGE`，包含三路 `*_mm`、`*_status`、
`*_age_ms`、ToF 设备状态、`risk` 和 `gating=0`。启动日志包含
`RANGE_MODE,mode=LOG_ONLY,gating=0`，`!Q` 包含 `range_motion_gating=0`，用于确认
烧录版本。完整验收步骤见
[传感器集成测试方案](传感器集成测试方案.md)。

### 当前逻辑量到实车速度的映射

Android 实车页面当前使用：前进 `14,14`、后退 `-12,-12`、转向 `-5,5` 或
`5,-5`。固件映射为：

| Android `c` | AT8236 四轮目标（M1,M2,M3,M4，mm/s） | 说明 |
|---|---|---|
| `c14,14` | `240,-240,-240,240` | 当前 Android 满档，240 mm/s 前进 |
| `c-12,-12` | `-206,206,206,-206` | 约 206 mm/s 后退 |
| `c21,21` | `600,-600,-600,600` | 扩展直线硬上限，仅分级验证后开放 |
| `c-21,-21` | `-600,600,600,-600` | 扩展后退硬上限，仅分级验证后开放 |
| `c-5,5` | `-86,-86,86,86` | 保留低速左转档 |
| `c5,-5` | `86,86,-86,-86` | 保留低速右转档 |
| `c-14,14` | `-240,-240,240,240` | 中高速原地左转 |
| `c14,-14` | `240,240,-240,-240` | 中高速原地右转 |
| `c-21,21` | `-240,-240,240,240` | 原地左转，受独立转向上限约束 |
| `c21,-21` | `240,240,-240,-240` | 原地右转，受独立转向上限约束 |
| `c0,0` | `0,0,0,0` | 主动制动 |

非零普通侧速度最低 40 mm/s，纯原地转向最低 80 mm/s。现有 `c0..14` 映射保持
不变，`c14` 仍为 240 mm/s；逻辑量 `15..21` 使用扩展区间，`c21` 的直线、后退
或同向差速上限为 600 mm/s。任何左右侧反向对转都单独限制在 240 mm/s，避免
跟随提速意外形成高速自旋。Android 的搜索 `±5` 仍约为 86 mm/s。

> 343、446、549、600 mm/s 都需要重新完成悬空方向/反馈/制动和空旷场地
> 短距离验证，不能直接以 `c21` 在地面长距离运行或在人群、货架附近测试。

### 自动跟随动态缓弯

上位机动态缓弯继续使用同一个 `c<left>,<right>` 协议。当前换算在 `10..14`
区间保持线性差速，40 mm/s 最低保护不会介入：

| Android `c` | 左/右侧目标 mm/s | AT8236 `$spd`（M1,M2,M3,M4） |
|---|---:|---|
| `c14,14` | `240 / 240` | `240,-240,-240,240` |
| `c10,14` | `171 / 240` | `171,-240,-171,240` |
| `c11,14` | `189 / 240` | `189,-240,-189,240` |
| `c12,14` | `206 / 240` | `206,-240,-206,240` |
| `c13,14` | `223 / 240` | `223,-240,-223,240` |
| `c14,10` | `240 / 171` | `240,-171,-240,171` |

因此 `c10,14` 与 `c14,10` 是互为镜像的缓弯，内外侧约为 `0.71:1`；不会被
最低速度保护或原地转向 80 mm/s 地板拉成同速。控制循环从旧目标向新目标以
20 mm/s 每 50 ms 过渡，稳定后使用上表目标。横移暂不接入，也不新增横移协议。

若上位机的新协议改为分别发送“速度 + 方向”，协议解析层最终应换算成左右有符号
逻辑量或左右 mm/s 目标，再进入现有单一控制入口。协议定稿前不要在本固件中并行
增加第二套电机状态机。使用现有 `c` 协议时，推荐速度档位为：

| 逻辑量 | 单侧目标 mm/s | 用途 |
|---:|---:|---|
| 9 | 154 | 第一阶段回归档 |
| 14 | 240 | 当前 Android 满档 |
| 15 | 291 | 扩展区间入口 |
| 16 | 343 | 第一阶段提速验证 |
| 18 | 446 | 第二阶段高速验证 |
| 20 | 549 | 最终上限前验证 |
| 21 | 600 | 直线/同向差速硬上限，仅最终验证后开放 |

## 防止指令混乱的机制

1. Android 的 `BleSerialWriteQueue` 保证同一时间只有一个 GATT 写请求在途；STOP
   和急停优先，普通运动只保留最新一条。
2. ESP32 BLE 回调只把字节送入队列，不直接控制电机；主循环是唯一命令解析和
   电机状态修改入口。
3. 每次 BLE 连接都有新的 `epoch`。断线前尚未处理的字节在重连后会被丢弃，旧会话
   的运动命令不能复活。
4. 连续到达的普通运动采用 latest-wins：控制循环执行前只保存最新目标。
5. `c0,0` 不走减速斜坡，立即发 `$spd:0`；`!S` 进入锁存状态，之后所有运动均拒绝。
6. 心跳和运动保鲜分开：心跳超时按 `h` 值（默认 750 ms），运动命令 500 ms 未刷新
   也会停车，所以心跳不能让一条旧的非零运动永久生效。
7. 直接换向不缓存反向命令。先制动并用新鲜 `$MSPD` 确认四轮低于 30 mm/s、持续
   400 ms；Android 在此期间仍会每 100 ms 重发，只有制动完成后收到的新帧才执行。
8. BLE 断开、接收队列溢出、运动时遥测丢失、反馈反号或硬超速都会停车。硬超速采用
   3.0 倍目标值的动态阈值，并受 300 mm/s 下限和 750 mm/s 绝对上限约束；1.5 倍只告警。
9. 运动中 `$MSPD` 短暂丢失时先进入零速制动；制动遥测持续丢失 1500 ms，或制动
   2 秒仍未确认静止时，进入可恢复 `DRIVER_ERROR`，发送 `$pwm:0`。只有 `$MSPD`
   恢复且四轮连续低于 30 mm/s 达 1000 ms 后才回到 `READY_STOP`，原运动命令不会
   重放，必须收到新的 `c` 命令才能再次运动。
10. 反馈方向反号、持续硬超速、启动阶段驱动不就绪仍是不可自动恢复的硬故障；
    `!S` 急停仍必须重启 ESP32，不能被普通驱动恢复逻辑清除。
11. `DRIVER_ERROR` 和急停期间仍接受 `c0,0`、`h`、`s` 与只读查询；非零运动继续
    拒绝。重复 `latched_stop` 错误按 500 ms 限频，避免错误通知占满 BLE 链路。

`!Q` 会永久保留最近一次故障快照：`last_fault_reason`、`last_fault_at_ms`、
`last_fault_recoverable`、`fault_target`、`fault_mspd`、`fault_mspd_age_ms` 和
`driver_recovery_active`。即使故障已经恢复到 `READY_STOP`，这些字段也不会立即清除，
便于事后定位首次触发原因。

## 编译与烧录

1. 先架空四轮，旁边保留可直接断开电机电源的人。
2. Arduino IDE 打开本目录的 `.ino`。
3. 开发板选择 `ESP32 Dev Module`，串口选择 ESP32 对应 COM 口。
4. 使用 ESP32 Arduino Core 自带的 `BLEDevice`、`BLEServer`、`BLE2902`；另安装
   **Pololu VL53L1X 1.3.1**（头文件 `VL53L1X.h`）。不要同时安装同名但 API 不兼容的库。
5. 编译并上传，串口监视器设为 115200。
6. 上电后应看到 boot 文本；发送 `!D,1` 和 `!Q`，等待
   `state=READY_STOP,driver_ready=1` 后才允许运动；本版 `!Q` 还应包含
   `speed_legacy_input=14,speed_legacy_mmps=240,speed_full_input=21,`
   `speed_cap_mmps=600,overspeed_warning_ratio=1.50,overspeed_hard_ratio=3.00,`
   `overspeed_absolute_mmps=750.00`，并检查 `last_fault_reason`、`driver_recovery_active`、
   `left_status/center_status/right_status`，用于确认烧录的是本次故障恢复与三路测距
   集成版本。

无需 Arduino 工具链的静态契约检查可在仓库根目录执行：

```bash
python -m unittest firmware/esp32_at8236_velocity_ble/tests/test_firmware_contract.py
```

它检查引脚、地址、阈值、V1 `s` 链路、V2 禁止项和主循环安全调用顺序，但不能替代
ESP32 实际编译、I²C 实物测距或停车距离测试。

## 分阶段验证步骤

### B0：无运动握手

1. 电机电源先断开或四轮保持架空，ESP32 上电。
2. Android 扫描并连接 `OpenBot: CART_AT8236`。
3. 确认 Android 显示 `BLE 已就绪 · CART_AT8236`。
4. USB 执行 `!Q`，确认 `ble_connected=1`、`driver_ready=1`。
5. 连续连接、断开、重连 3 次；任何时刻都不应出现非零 `$spd`。

### B1：悬空方向和速度

1. 四轮架空，USB 执行 `!D,1`。
2. Android 前进按住 1 秒再松开：日志目标应为
   `240,-240,-240,240`，松开立即出现 `brake_start`，随后 `brake_settled`。
3. 后退按住 1 秒再松开：目标应约为 `-206,206,206,-206`。
4. 左转、右转各按住 1 秒：目标应分别约为 `-86,-86,86,86` 和反号。
5. 每次动作后执行 `!Q`；必须回到 `READY_STOP`，四轮 MSPD 绝对值应不超过
   30 mm/s 附近的量化波动。

### B1.1：动态缓弯差速

保持四轮悬空并开启 `!D,1`，每条命令持续刷新至少 2 秒，动作之间发送
`c0,0` 并等待 `brake_settled`：

1. `c14,14`：诊断 `target` 应为 `240,-240,-240,240`。
2. `c10,14`：诊断 `target` 应为 `171,-240,-171,240`；M1/M3 是内侧轮。
3. `c14,10`：诊断 `target` 应为 `240,-171,-240,171`；M2/M4 是内侧轮。
4. `c-5,5`：诊断 `target` 应为 `-86,-86,86,86`。
5. `c5,-5`：诊断 `target` 应为 `86,86,-86,-86`。
6. 对第 2、3 组各截取启动 600 ms 后至少 5 条 `drive` 日志，分别计算内侧与
   外侧 `$MSPD` 绝对值平均数。两组的内外侧关系应互换，内侧平均速度应明显小于
   外侧；不要要求每个瞬时值严格等于 171/240，因为 `$MSPD` 约按 19.04 mm/s 量化。
7. 若 `target` 正确但 `$MSPD` 长期同速或内外关系没有镜像，先保存完整日志，检查
   机械空转、编码器和 AT8236 PID；不要直接加入旧版起步补偿。

### B1.2：新增高速区间准入

不要一开始就在地面发送 `c21,21`。保持四轮悬空、`!D,1` 已开启，并确保 Android
或 BLE 调试端持续发送 `h750`，按以下顺序逐档验证：

1. 依次刷新 `c9,9`、`c14,14`、`c16,16`、`c18,18`、`c20,20`、`c21,21`；
   对应稳定目标应约为 154、240、343、446、549、600 mm/s（四轮符号仍按
   M1/M4 正、M2/M3 负）。低于 450 mm/s 每档保持 2 秒，更高档保持 2.5 秒，
   以覆盖 20 mm/s 每 50 ms 的渐进加速时间。
2. 每档后立即发送 `c0,0`，必须先看到 `brake_start`，再在 2 秒内看到
   `brake_settled`；只有上一档完整停车后才能进入下一档。
3. 每档稳定段检查四轮 `$MSPD`：符号必须与目标一致，不能出现某一轮不转、持续
   反号或超过固件绝对反馈上限；出现任何反馈故障即停止升级。
4. 悬空全部通过后，落地只从 `c9,9` 开始，在空旷直线场地运行 0.5 秒并停车；
   再测试 `c14,14`，保持时间仍不超过 1 秒。
5. 只有 `c14` 的直行偏差、停车距离和制动日志都可接受，才允许依次测试
   `c16`、`c18`、`c20`、`c21`；不得跳档。每升一档都先做 0.5 秒，再做 1 秒。
6. 记录每档 1 秒位移、松键后停车距离、最大左右偏移和四轮 `$MSPD`。若停车距离
   明显增大、车身偏航、轮胎打滑或未出现 `brake_settled`，退回上一通过档作为
   上位机速度上限，不要放宽制动阈值掩盖问题。
7. 分别计算 `c14`、`c16`、`c18`、`c20`、`c21` 各自最后 5 条 `drive` 日志的
   四轮 `$MSPD` 绝对值平均数。如果诊断 `target` 持续提高，但连续两档的实际平均速度
   提升都不足约 10%，说明软件目标已不再是主要瓶颈，应转查电池压降、AT8236 PID、
   电机负载和机械阻力；继续增大软件数值通常不会让车明显更快。

### B1.3：提高后的原地转向

1. 四轮悬空，依次测试 `c-5,5`、`c5,-5`，确认目标约为 `±86 mm/s` 且方向互为镜像。
2. 再依次测试 `c-14,14`、`c14,-14`，确认目标为 `±240 mm/s`；最后仅在悬空状态
   短测 `c-21,21`、`c21,-21`，目标仍应限制在 `±240 mm/s`，不能升到 600 mm/s。
3. 每条转向命令保持不超过 1 秒，随后发送 `c0,0` 并等待 `brake_settled`；左右方向
   之间不得直接换向。
4. 落地从 `c±5` 开始，每次 0.3 秒；确认没有侧翻趋势、剧烈打滑或线束缠绕后，
   才测试 `c±8`，再测试 `c±11`。首轮落地测试不使用 `c±14` 或 `c±21` 原地转向。

### B2：顺序与换向

1. 前进按住 1 秒，不松手直接切到后退。
2. 应先看到 `brake_start,reason=control_zero` 或 `direct_reversal`；制动期间的反向帧
   只返回 `!ERR,settling`，不能立即反转。
3. 看到 `brake_settled` 后，下一条 Android 100 ms 刷新帧才启动后退。
4. 快速执行“左转 -> 右转 -> 松开”10 次，最终状态必须为 `READY_STOP`，不能在
   松开后重放旧方向。
5. 运动中断开 BLE，目标必须立即变零并制动；重新连接后必须重新按键才可运动。

### B3：超时和急停

1. 用 BLE 调试工具或暂时停止 Android 控制刷新，只保留 `h750`；非零运动最晚应在
   500 ms 左右因 `motion_timeout` 停止。
2. 停止全部 BLE 写入，最晚应在 750 ms 左右因 `link_timeout` 停止。
3. 运动中发送递增的 `!S,1`，应进入 `EMERGENCY_STOP` 并下发 `$pwm:0`。
4. 再发送任意 `c` 必须被拒绝；重启 ESP32 后才能恢复。

### B3.1：可恢复驱动故障

本项先架空四轮，必须保持 USB `!D,1` 日志和物理断电能力：

1. 正常刷新非零 `c` 命令，临时中断 AT8236 TX 到 ESP32 RX，使 `$MSPD` 超过
   500 ms 未更新；固件必须先记录 `brake_start,reason=telemetry_timeout_while_moving`，
   目标轮速立即清零，不能继续运动。
2. 在 1500 ms 内恢复串口且四轮已经静止，状态应通过正常 `BRAKING` 回到
   `READY_STOP`，不得自动恢复故障前的非零轮速。
3. 让遥测中断超过 1500 ms，应进入 `DRIVER_ERROR`，`!Q` 应显示
   `last_fault_reason=mspd_lost_while_braking,last_fault_recoverable=1`。
4. 恢复 `$MSPD` 后，只有四轮连续低于 30 mm/s 达 1000 ms 才能出现
   `driver_recovered` 并回到 `READY_STOP`；恢复前非零 `c` 必须被拒绝。
5. 回到 `READY_STOP` 后保持不发送命令，四轮必须继续为零；再发送一条新的非零
   `c`，才允许重新运动。
6. 在可控测试台模拟反馈反号或持续硬超速时，`last_fault_recoverable` 必须为 0，不能
   自动恢复。反馈超过 1.5 倍动态阈值但未超过 3.0 倍/750 mm/s 硬阈值时，只应出现
   `overspeed_warning`，不得进入 `DRIVER_ERROR`。不要在落地车辆上主动制造硬超速。
7. 发送 `!S,<seq>` 后即使 `$MSPD` 新鲜且为零，也必须保持 `EMERGENCY_STOP`，只能
   重启恢复。

### B4：空载落地

1. 只在 B0-B3 全部通过后落地；空旷平整地面，测试者站在侧后方并可物理断电。
2. 前进、后退各按住 1 秒，测量是否直行；再各按 2 秒。
3. 左转、右转各按住 1 秒，确认方向和制动；再做一次左转后右转回正。
4. 做四组弧线：`左侧较慢/右侧较快` 和镜像方向，各 2 秒。
5. 若轨迹与 A-M 阶段明显不同，先保存 USB `BLEVEL` 日志，不要立即加入轮间补偿。

## 通过条件与停止条件

通过条件：握手稳定、方向全部正确、四轮无反号/硬超速、松键/断线/超时均能制动，
快速换向没有旧命令重放，落地直行和转弯与阶段 A-M 基本一致。

立即停止并断电：任一轮方向错误、`$spd:0` 后仍持续加速、出现
`feedback_sign_mismatch` / `overspeed` / `pid_brake_failed`、BLE 断开后仍运动、
或急停后还能接受运动。此时保留完整 USB 日志，不继续阶段 N。
